## 产品概述

万象巡检 Agent 面向连锁门店巡检与运维人员。用户无需选择意图，直接用自然语言查询设备、能力、告警、证据和统计结果。首个线上租户为 OPPO。

MVP 范围为 DeepVision 在线只读查询、临时直播/回放会话、当前快照、模型结构化意图适配、工具路由、订阅槽位管理、Pipeline 草案、证据展示和审计。线上订阅写入、告警反馈、任意 SQL、模型训练和 Pipeline 发布不在本次发布范围。

## 用户与权限

首版以租户管理员验收，只能访问授权 OPPO 组织。查询可自动执行；任何写操作必须有服务端权限、计划确认、幂等和线上回执。当前写接口未确认，因此所有写操作阻断。

禁止返回摄像头用户名、密码、IP、RTSP、`camera_config`、AppSecret、Token 和人员敏感信息。

## 信息架构

一级视图为巡检助理、告警与证据、数据分析、巡检能力和操作记录。启用开放检索的租户另有独立一级入口“开放检索记录”；它仅展示当前用户自己的公开检索流水，不复用巡检“操作记录”、告警与证据或巡检知识库。组织上下文来自线上 POI 树；切换门店后新建对应上下文会话，原会话保留在历史列表。

## 页面需求

1. 巡检助理：单一输入框、示例任务、自动意图、工具轨迹、自然澄清和历史对话。首次提问自动生成标题；点击“新建对话”不得删除当前记录；历史列表展示最近 50 条并支持滚动、收起和单条关闭；点击历史项恢复消息、计划和脱敏结果卡；刷新页面默认恢复最近一条有消息的会话。
2. 告警与证据：真实告警列表、门店、摄像头、时间、状态和签名证据图；支持全量服务端分页、首页/上页/下页/末页、页码跳转，每页可选 10/20/50/100 条。
3. 数据分析：总数、门店排行、时间范围和统计口径；不可用指标显示“暂未提供”。
4. 巡检能力：展示门店线上已配置能力，不提供创建按钮。
5. 异常状态：上游失败、部分成功、授权失败、空数据和只读阻断必须明确展示，不回退演示数据。

## 核心业务流程

1. 用户输入自然语言。
2. 模型输出结构化意图与槽位，Validator 校验组织、能力和风险。
3. 编排器选择白名单只读工具。
4. PaaS Connector 获取真实数据并脱敏。
5. Agent 汇总有限结果并绑定来源、范围、时间和证据。
6. 写操作返回只读阻断，不产生线上或本地副作用。

## 数据模型

核心对象为 Tenant、Organization/POI、Camera/Sensor、Capability、Alarm/Event、Evidence、Conversation、Message、AgentRun、ToolCall 和 AuditLog。线上业务事实以 DeepVision PaaS 为准，会话与审计由 Agent 服务持有。

## 接口

保留 `/api/bootstrap`、`/api/conversations`、`/api/conversations/{id}`、`/api/conversations/{id}/messages`、`/api/events`、`/api/events/{id}`、`/api/subscriptions` 和 `/api/audit-logs`。响应增加 `integration` 与 `agent` 元数据，标识数据源、意图引擎、工具和只读状态。会话详情仅允许创建人读取。

## 非功能要求

- 单次 PaaS 请求超时 20 秒，错误必须净化。
- Token 缓存并提前刷新，浏览器不能持有供应商 Token。
- 告警页面单次最多返回 100 条；模型上下文最多使用 50 条样本，大范围分析优先聚合。
- 页面支持 390x844 及 1280x720，无横向溢出。
- 线上查询和证据访问写审计，不记录密钥和原始扩展字段。
- 历史对话最多加载最近 50 条；持久化结果卡不得包含播放地址、设备凭证和供应商 Token。
- 关闭对话采用软关闭：仅会话所有者可执行，关闭后从列表移除但保留消息与审计记录。

## 验收标准

1. OPPO 组织、30 路摄像头、配置能力和真实告警可查询。
2. 用户不需要选择意图；模型配置后使用结构化模型输出，未配置时明确显示降级。
3. 告警详情可打开真实证据，敏感字段扫描为零。
4. 全租户查询正确覆盖 2 个门店，统计口径可见。
5. 创建任务和反馈告警不会产生写副作用。
6. 自动化、桌面和移动端回归通过。
7. 告警分页总数、总页数和 PaaS 一致，四档页大小切换后回到第一页且不重复、不漏页。

### 意图判定契约

意图服务采用“结构化大模型判断 + 确定性业务护栏”。大模型负责理解自然语言、组织、镜头位置、时间和能力目标；护栏负责保证媒体类型、历史时间、写操作风险和槽位状态不会被模型改写。租户接入是安全管理指令，必须在通用巡检意图之前识别；完整 AppKey/AppSecret 凭证束或“连接/链接/接入租户”均命中 `CONFIGURE_TENANT_INTEGRATION`，不得生成巡检 Pipeline。其余执行优先级固定为：视觉内容判断 -> 历史回放 -> 实时视频 -> 当前/指定时刻图像 -> 应用与设备查询 -> 订阅与 Pipeline -> 告警查询与分析 -> 帮助。

对话中已返回快照或直播时，后续“视频里/画面里有没有…”必须进入 `ANALYZE_VISUAL`。快照场景分析已展示图片；直播场景继承同一镜头并重新抓取最新帧，不得再创建新直播代替判断。

视觉判断必须区分“目标事实”和“业务异常”。垃圾、吸烟、打架等禁止出现目标被观察到时判为异常；员工接待、人员值守、员工在岗、佩戴工牌等必须满足行为未被观察到时判为异常。不得把 VLM 的否定回答直接显示为“未发现异常”。

必须行为还要判断前置服务对象：顾客在场且未执行接待、倒水、引导或讲解时判为异常；确认无顾客时标记为不适用且不触发异常；顾客是否在场无法确认时必须显示“证据不足、需要复核”，不得显示绿色正常状态。

倒水属于瞬时行为，允许使用服务结果作为代理证据：顾客手中、座位旁或其正在使用的桌面上出现水杯、水瓶或饮品，可视为已完成饮水服务；员工工作区、陈列区或远离顾客的杯子不得作为完成证据。结果需标记 `DIRECT_ACTION` 或 `SERVICE_OUTCOME`，便于解释可信度。

对“是否存在/是否出现/有没有”一类开放视觉问题，系统必须直接携带用户原始查询动态生成定位任务，不能把衣服颜色、背包款式、手持物或其他属性写成固定类别。每张相关快照先执行目标/人员枚举；首次返回否定、字段冲突或缺少定位证据时，必须执行独立的逐对象复核。肯定结论至少返回一项 `target_evidence`（对象、属性或关系、画面方位及可选 0–1000 归一化框）；否定结论必须返回覆盖完整度、已核验对象数和排除理由的 `absence_evidence`。任何一项缺失、画面遮挡或复核失败均显示“需要复核”，不得把“未检出”显示为“不存在”。

“查看当前镜头画面，找/寻找/查找/定位/识别/检测一个……”以及对画面对象数量、颜色、款式、类型、状态或关系的询问，必须被判定为 `ANALYZE_VISUAL`，不得因为同一句包含“画面/快照”而降级成 `CAPTURE_SNAPSHOT`。查询未明确指定摄像头、楼层或局部点位时，执行范围为目标门店内全部在线镜头：先全量抓图，再按模型单批上限分批判断并确定性合并。模型返回的摄像头名称必须同时满足“当前用户输入明确提及”与“当前范围摄像头台账唯一匹配”，才允许收窄为单镜头；历史消息中出现过的真实镜头名不能单独作为本轮限定条件。模型单批图片上限只是调用分批参数，不是摄像头覆盖上限。若任一可用镜头抓图或分析失败，覆盖状态标记为 `PARTIAL`；已命中的肯定结论可保留，否定结论必须降级为 `UNCERTAIN`，不得宣称全范围未发现。

当运行时已配置受控 OVD 时，所有开放存在性查询均可先生成候选框：人员问题固定含 `person`；物体问题由模型输出最多 3 个最小英文通用名词，并由服务端过滤指令、URL、非英文、超长和超量提示词后才调用 OVD。随后将候选对象裁剪放大并与完整画面组成单图证据板，让 VLM 按完整原始 query 判断颜色、服装、背包款式、携带物、物体属性和关系。OVD 只能提高候选召回率，不能直接回答开放属性问题；检测失败、空框、规划失败或不可读取快照必须保留 VLM 复核/不确定状态，不能生成否定结论。供应商令牌只能由服务端环境变量读取，严禁进入页面、对话历史、数据库、日志或仓库。

存在性事实命中不是业务异常。页面应将其标为“目标证据”并展示镜头与定位依据；只有禁止目标、必须行为缺失或受控 SKU 风险才使用异常红框和“异常证据”标签。

对话中的监控快照必须支持点击放大。大图预览需保留门店、镜头和拍摄时间，支持放大、缩小、恢复大小，并可通过关闭按钮、`Esc` 或点击遮罩退出；键盘用户可聚焦图片并按 Enter/空格打开。

| 典型输入 | 必须识别 | 执行要求 |
|---|---|---|
| “给我看下门口的监控视频” | `VIEW_LIVE_STREAM` | 无历史时间时默认直播；自动匹配门口镜头并创建临时流 |
| “看昨天 10:00 到 10:10 门口录像” | `VIEW_PLAYBACK` | 解析起止时间；自动匹配镜头后创建回放 |
| “获取昨天 10:05 门口的画面图像” | `CAPTURE_SNAPSHOT` | 保留指定时刻；通过录像抽帧，不得用当前快照替代 |
| “看下店门口的摄像头画面” | `CAPTURE_SNAPSHOT` | 返回当前画面，不返回设备清单或异常分析 |
| “这个画面有没有垃圾” | `ANALYZE_VISUAL` | 继承上一轮图像并执行视觉判断 |
| “视频里有没有员工在接待顾客” | `ANALYZE_VISUAL` | 未观察到接待行为时显示“发现异常”，并给出业务判定依据 |
| “查看当前门店在线摄像头” | `QUERY_CAMERAS` | 仅返回设备清单和状态，不创建媒体会话 |

镜头名称无法直接匹配“门口/收银台”等位置时，Agent 可读取候选镜头当前快照做语义相关性排序。该步骤仅用于选择镜头，不得生成异常结论；相关性低时必须说明展示的是最高相关候选，不得声称已经精确定位。

### 已有能力订阅槽位

订阅计划必须管理生效时间区间、摄像头、参数阈值和标定区域。任一槽位缺失时，Agent 一次追问一个最优先槽位，并利用会话历史继续填充。命名区域未完成多边形标定时状态为 `NEED_CALIBRATION`；全部槽位完整但写接口缺失时状态为 `NEED_INTEGRATION`，禁止显示已上线。

### 新能力 Pipeline

Pipeline 固定遵循“需求输入 -> 摄像头受控拉流 -> 解码与抽帧 -> 标定区域 -> 小模型原子能力 -> 时序规则 -> 视觉大模型复核 -> 置信度融合与去重 -> 结果和证据输出”。发布前必须通过视频源、解码压测、原子能力评测、VLM 成本、1:1 回放和人工审批门禁。

## 推荐开发顺序

在线只读数据 -> 模型网关与评测 -> SSO/RBAC -> 当前写接口契约 -> 计划确认与线上回执 -> WebSocket/ODPS -> 数据质量与 badcase 闭环。

## 周期快照 AI 巡检（v1.3）

用户可通过自然语言创建 Agent 自有调度任务，例如“帮我每隔 3 小时看下门店地面是否干净有垃圾，持续一周，从今天开始”。该任务不等同于 DeepVision 应用订阅：Agent 按时调用现有快照接口，将快照归档后交给 VLM 分析，并把每轮结果回写到创建任务的对话。

必填槽位为门店、在线摄像头、巡检目标、执行间隔、每日执行窗口、生效时间区间。用户未说明每日执行窗口时，只追问“按门店营业时间还是全天执行”；槽位齐全后展示计划卡，用户一次确认后创建任务。间隔任务可立即执行首轮；“每天 11 点”等固定时刻任务默认等待第一个 11:00，不得因创建时间而提前抓图。只有用户明确表达“现在/立即/先巡检一遍”时，才允许在固定时刻前追加一轮即时巡检。

每轮必须遵循“调度触发 -> 摄像头抓图 -> 本地证据归档 -> 归档字节送入 VLM -> 业务状态判定 -> 对话回写”。用户看到的图片必须与模型输入是同一归档文件，以 SHA-256 标识；禁止用后来重新请求的快照替换模型输入。结果卡和历史详情必须同时展示计划时间、实际开始时间、首帧抓图时间与偏差，时间真值取调度器和快照接口的 `captured_at`，不得通过 OCR 推测摄像头水印。图片支持点击放大，结果展示门店、镜头、拍摄时间、结论、可信度、画面依据和失败镜头。

当批次判定为异常时，必须把模型命中的镜头映射为异常证据图片，不得将整批所有图片全部标红。异常图片的红色边框、“异常证据”标签和语义标记须在对话结果卡、“告警与证据”列表及详情中保持一致。

多门店结果卡默认每家展示最多 4 张快照；超过部分必须以可点击的“+N”按钮呈现，点击后在原门店卡内展开该店全部模型输入快照，并支持再次收起。若该门店存在违规镜头，问题快照必须优先出现且保留红框、“异常证据”标签和问题数量；展开、收起及大图预览不得丢失该标记。

每条已发送的用户消息和 Agent 回复都必须显示服务端系统时间，精确到秒，以 `Asia/Shanghai` 时区展示。周期巡检异步回复的时间以分析完成并对用户可见的时刻为准。

聊天是周期巡检任务的创建与通知入口，不是巡检历史的唯一载体。每次调度执行以 `inspection_run` 形成一条独立历史记录，并永久关联该轮全部 `scheduled_evidence`；例如一次巡检抓取 7 路镜头，应在列表中显示 1 条巡检记录和 7 张证据，不得拆成 7 条记录。关闭或软删除原聊天后，任务、运行记录与证据仍可从“告警与证据 -> AI 巡检记录”分页追溯。

“告警与证据”页面采用“告警事件 / AI 巡检记录”分段切换。AI 巡检记录支持按当前门店过滤、按完成时间倒序、10/20/50/100 条分页；列表显示组合缩略图、证据数量、任务、结论、时间、可信度和状态，详情展开当次全部图片、业务判定、画面依据、模型版本与失败说明。正常、异常、待复核、部分完成和失败批次均须保留。

任务支持立即执行、暂停、恢复和取消。取消不可恢复；暂停或取消发生在本轮分析期间时，本轮证据仍保留，但不得自动恢复后续调度。部分镜头失败时继续分析成功归档的画面并标记部分成功；全部抓图或 VLM 失败时不得输出正常/异常结论。执行中断超过 15 分钟后自动记录失败并恢复下一周期。

验收要求：示例对话只补问每日执行窗口；确认前不创建任务；确认固定 11:00 后任务为 `ACTIVE` 且 `next_run_at` 为首个 11:00，不能立即抓取 11:59 的快照；显式“现在先巡检”才允许立即首轮；任务详情、原对话和 AI 巡检记录均可查看每轮运行与计划/实际时间；关闭原对话后历史仍存在；单次 7 张图片只生成 1 条历史记录；所有模型输入快照可访问、可放大且哈希稳定；异常批次只标记命中的对应图片，三个入口一致；每条问答显示到秒的系统时间；异常计数只统计 `POSITIVE`，证据不足计入 `UNCERTAIN`。

## 租户与门店接入管理（v1.4）

租户管理员可在“接入管理”查看已接入 DeepVision 租户，每个租户展示租户名称、租户编码、脱敏 AppKey、凭证托管来源、连接状态、最后同步时间和门店数。门店列表展示名称、组织编号、摄像头数量和同步状态。页面禁止返回 AppSecret、原始 AppKey、密文、主密钥或凭证引用。

工作台将“当前租户”与“当前门店”作为连续的两级上下文。新租户接入后必须立即出现在租户选择器，切换后展示该租户已同步的全部门店；每个租户独立记住上次选中门店。租户切换必须同步切换 Agent 凭证、会话、告警、订阅、巡检记录和审计范围，不得仅替换页面文案。顶部和输入区持续显示当前租户/门店，切换期间清空旧租户页面状态，禁止出现短暂串数据。

新增接入通过 Agent 对话发起。当本轮同时包含租户编码、AppKey 和 AppSecret 时，Agent 必须直接验证连接、同步门店并返回接入结果，不再追问或输出能力 Pipeline。缺少任一必填字段时才返回安全配置卡。前端乐观消息和后端持久化消息都必须先隐藏 AppKey/AppSecret；后端只在验证与同步全部成功后加密入库。验证失败不得保存凭证或部分租户数据。

权限仅开放给租户管理员和系统管理员。对话中若包含 `AppKey:` 或 `AppSecret:`，服务端在写入消息前必须替换为安全提示；审计只记录租户编码、门店数量和执行状态。对话重复接入已存在租户时按幂等成功返回，不覆盖原凭证；专用管理 API 的重复创建仍返回冲突。

验收要求：环境变量中的 OPPO 接入和凭证库中的新租户均可被列出；租户切换后门店下拉、Agent 查询和历史数据均来自选中租户；页面可展示真实同步门店和摄像头数量；非管理员访问返回 403；未知租户上下文返回 403；页面、消息、审计和 API 均无原始密钥或密文；主密钥文件权限为 `0600`。

## 大规模门店选择与楼层点位视觉巡检（v1.5）

门店数量超过单屏容量时，不得使用浏览器原生长下拉。工作台门店选择器采用固定高度弹层，支持按门店名称或组织编号即时搜索；结果行展示门店名称、组织编号和摄像头数量，当前门店高亮，空结果给出明确状态。切换门店后继续沿用当前租户上下文，并清空旧门店会话态数据。

用户提出“检查 B1 层是否存在垃圾桶溢满”等楼层巡检时，Agent 必须先从摄像头点位名称与位置标签中解析楼层编码，再对匹配镜头抓图。`B1`、`B01`、`B001`、`负一层`和`地下一层`视为同一楼层；无匹配点位时明确停止，不得拿其他楼层画面代替。

楼层点位视觉巡检遵循“楼层解析 -> 点位筛选 -> 全部匹配点位抓图 -> 分批视觉分析 -> 业务汇总 -> 证据展示”。页面展示的图片集合必须与实际模型输入集合一致，并显示楼层、匹配点位数量和点位名称。模型命中的异常镜头需显示红框和“异常证据”标签；该标记随会话历史持久化，刷新或重新打开对话后保持一致。

同一批次包含多张预警或巡检图片时，大图预览必须支持“上一张/下一张”切换，并显示当前序号与批次总数。切换范围只限于用户所点击图片所在批次，不得跳入其他消息或记录；首尾按钮需正确禁用，同时支持键盘左右方向键。切换图片时镜头、门店、拍摄时间、异常状态和缩放比例必须同步刷新。

楼层名称属于门店内的位置范围，不属于租户组织范围。意图模型将 `B1层` 等楼层误填到门店槽位时，执行护栏必须剔除该值并继续使用当前租户下的当前门店；若同时包含真实门店名和楼层，仅剔除楼层项。明确楼层的新查询必须重新抓取该楼层当前快照，不得因句子包含“画面中”而复用上一轮其他时间或楼层图片。

商户名、柜台名和局部点位名同样属于当前门店内的摄像头位置，不属于租户组织。模型将“三月兽”“汪保来”等点位误填到门店槽位时，只有在当前门店摄像头名称中匹配成功后才转为点位条件；页面展示实际命中的点位快照。用户使用“那汪保来呢？”等省略追问时，必须继承上一问明确的视觉目标，只切换点位，不得扩展为人员在岗、服务接待或其他未询问事项。

在线模式页面标题、副标题、租户徽标、门店和输入区范围必须使用同一当前租户状态，不得保留 OPPO 等静态租户文案。

## 固定时刻巡检与 SKU 结果标注（v1.6）

“每天 11 点巡检”中的 `11:00` 是调度触发时刻，不是“在当天任意时刻创建后立即抓一张”的近似描述。计划卡、调度任务和运行记录必须保留同一个 `scheduled_at`；实际执行和抓图发生晚于计划时，页面显示真实偏差而不覆盖或伪造计划时间。若首帧来自 11:59，结果必须明确展示“计划 11:00 / 实际 11:59 / 延迟 59 分钟”，便于定位上游、队列或服务恢复问题。

知识库的图片型物品可填写可选 SKU。视觉模型仅可从本轮已召回参考图片的受控 SKU 集合中返回匹配值；只有现场图清晰识别到对应物品时才允许标注，不能依据知识标题、镜头名称或相似外观猜测。服务端仅持久化“本轮已归档镜头 + 受控 SKU”的映射，图片原始字节和 SHA-256 不修改；对话结果卡、批次卡、巡检历史缩略图、详情和大图预览均在图片右上角显示 `SKU：...`。未配置 SKU、未匹配、低置信或无法辨识时不得显示标签。

## 精确样板比对的单图 SKU 知识库（v1.3.2）

一条知识可以包含多个 SKU 或同一 SKU 的多个视角，因此 SKU、特征说明和拍摄视角必须维护在单张参考图上，而不是仅维护在知识条目上。创建和编辑知识时，用户可以为每张本地上传图或图片地址分别填写 `SKU / 视角 / 特征说明`；默认 SKU 仅用于历史知识和未单独填写的图片。

巡检计划固化已召回知识的单图元数据。运行时，每张参考图的 SKU 都是视觉模型可返回的受控白名单，结果图仅在现场画面清晰匹配到该参考物品时展示该图对应 SKU。模型、截图或证据不足时必须不标注，不得使用知识标题或相似外观推断 SKU。

租户管理员在“租户能力”页按当前租户查看并启停开放检索、Office 文档处理、检索结果生成 PPT 与已批准模型网关处理。每项能力展示启用状态、影响说明、依赖关系、最后变更时间和最近 12 条变更审计；租户切换必须清空旧配置状态并重新读取新租户配置。

## 开放检索事实核验与回答（2026-08-20）

开放检索不以“改写成功”或“返回若干链接”视为完成。系统必须先识别事实类型、制定受控检索计划，并将每条安全结果按**相关性、时效性、事实/事件语义、来源信誉**综合评估，再以“主体、谓词、日期/值、地区、状态、引用”返回。`EVENT_DATE`（如“什么时候上映”“什么时间发布”）属于事件日期：已发生日期不受日级新闻窗口限制；`LIVE_STATUS`、价格/天气/航班、政策/任命分别使用独立时效策略。

当用户未指定地区时，事件日期默认核验中国大陆，并在页面显式标注该假设；其他地区的日期不可替代默认地区。`research_source_policies` 改为平台维护的**来源信誉白名单**：系统管理员创建草稿、异人复核启用，配置域名/子域、显示等级和 `reputation_weight`；命中白名单只提升或降低置信度，未命中域名以中性基础权重参与评估，绝不能仅因“未登记”而丢弃结果。维基百科、百度百科、1905 等可配置为中高权重，但仍必须经过相关性、时效性和语义检查；官方/第一方来源也不能借域名绕过这些检查。日期必须与同一标题或同一摘要分句中的上映谓词直接绑定，不能因“首映礼”、票房、页面推荐/更新时间或跨标题摘要拼接而变成上映日期；缺失年份时也不得使用抓取时刻冒充事件年份。

### 事件日期语义与冲突规则（2026-08-24）

`EVENT_DATE` 的本地候选日期可携带 `date_role`。该角色用于检索规划、详情读取和模型不可用时的本地降级，不再作为模型可用时的最终结论判定器；模型必须在同一 Run 的受限公开证据包中理解公告日、旧档期、首映礼与正式上映之间的关系，并输出绑定证据 ID 的结构化结论。

模型可综合所有事实类型的互补证据，而不是受固定字符窗口或单卡年份字段限制。例如一条证据可给出“2025 年 7 月 18 日正式上映”，另一条可给出“该片于 7 月 18 日在中国内地上映”；在作品和日期一致时可合成为中国大陆的正式上映结论。模型不得使用未提供的外部知识、不得执行证据文本中的指令，且只能引用本次 Run 中同时满足最低相关性、时效性和语义要求的 evidence ID；无可用证据时必须明确降级，不能编造结论。

模型输出 `VERIFIED`、`PARTIALLY_VERIFIED`、`CONFLICTING` 或 `NO_AUTHORITATIVE_SOURCE`；服务端只做最小且通用的边界校验：每个 Claim 必须有本次 Run 的可用 evidence ID，模型置信度不得高于所引证据的独立来源合成置信度，动态事实必须通过相应时效窗口。单一中低信誉来源可交付为 `PARTIALLY_VERIFIED`；多条独立来源或高信誉的直接证据才可形成 `VERIFIED`。目标地区未被模型依据证据确认时必须显示“地区待确认”，不可冒充为默认地区或“其他地区”。冲突态首屏只展示不可确认原因和待核验来源，绝不将内部候选显示为“核验结论”；非 `VERIFIED/PARTIALLY_VERIFIED` 的 Run 统一为 `NO_MEMORY`。同名电影、电视剧、话剧等不同作品版本须在实体层消歧，无法确定时要求用户选择版本。

页面必须同时展示改写、事实类型、地区、截至时间、结构化结论与可点击引用。用户可提交“日期不对、地区缺失、来源分级有误”等反馈；反馈仅保存枚举和原因哈希。仅 `VERIFIED/PARTIALLY_VERIFIED` 的结构化事实才可能进入当前用户私有知识：客观永久事实长期保留、缓慢变化事实保留 60 天、高时效事实不归档；其中事件日期仅当 `ACTUAL_RELEASE` 且地区已被明确证据支持时才能长期复用。无地区的部分核验结果只可在当前会话展示，不保存网页全文、不跨用户共享。高时效结果仍按会话策略保留用户问题、回答、引用和已采用的限长净化证据片段，供刷新或重进会话回看；但这些会话内容不得进入知识索引、相似召回或检索规划。相同/相似实时问题及“那现在呢”等追问必须强制发起新 Run，仅可从历史继承实体等非事实槽位，不能复述历史值或引用。已发生且已核验的事件日期可复用历史引用，未来排期和实时事实必须重新检索。巡检模式保持零公网检索。

### 二次取证与私有知识复用（P0.5，待开发）

当 Tavily 已返回相关 URL、但标题/摘要不足以支撑事实时，系统必须在 Open Research 域内执行受控详情取证：只读取本次搜索结果中的公开 HTTPS URL，受 SSRF、重定向、MIME、大小、超时及提示注入门禁限制；正文仅内存解析为最小事实片段，不写入数据库、记忆、审计或前端。中低信誉页面可在证据语义直接、时效合格时形成带引用的部分结论，或与独立来源交叉合成为确定结论；不会因 `SECONDARY` 标签被提前丢弃。

同一用户的历史核验事实在外部搜索前按 `EXACT_REUSABLE`、`SIMILAR_HINT`、`STALE_OR_REVOKED`、`NO_MEMORY` 分级：永久客观事实精确命中可直接回答；缓慢变化事实仅在 60 天内且未请求“最新/当前”时可复用；高时效事实不建知识索引。高时效会话消息可见但对检索引擎不可见，历史内容最多用于补全本轮实体，不得作为来源、数值或结论；每次必须重新检索。相似或过期记录只能帮助实体改写、来源选择和新一轮检索规划。详情见《开放检索二次取证与私有知识复用方案 v3》。

### 开放检索记录页（P0.5，待开发）

“开放检索记录”是面向用户的独立查询页，用于集中回看已完成的 Open Research Run；它不是聊天副本、巡检操作记录，也不是可复用知识库。列表仅在当前用户、当前租户范围内查询，默认按完成时间倒序并使用游标分页；支持按时间范围、事实类型、质量状态、反馈状态筛选，以及在本人原问题和改写实体中检索。租户切换、登出或权限失效时必须立即清空列表、详情、筛选缓存和分页游标。

列表字段为原问题、改写实体（如有）、事实类型、质量状态、截至时间、来源数量、反馈状态和生命周期标签。详情展示最终回答、可点击引用、最终 Claim 已采用的限长净化证据片段、改写原因、质量状态和“查看原会话”入口；不得展示网页全文、原始 HTML、Tavily 原始响应、未采用候选、内部 Trace 字段或其他用户的任何记录。无记录、无筛选结果、加载失败、403/404 和来源已失效都必须有独立、可理解的页面状态。

`NO_MEMORY`（天气、价格、余票、航班等）记录与其他记录一样可回看，详情卡固定显示“实时查询；再次提问将重新检索”。用户从详情发起“重新检索”或在原会话追问时，系统必须生成新的 `run_id`；只能继承实体、地区、产品或时间范围等非事实槽位，不能把旧数值、旧日期、旧引用或旧 Claim 当作本轮事实输入。知识页仅列出 `PERMANENT_FACT` 和未过期 `SLOW_60D`，不得出现这些实时记录。

验收要求：用户 A 能在刷新后看到自己的实时历史结果和引用，用户 B/其他租户访问相同 `run_id` 或列表均为 404/空集；租户管理员只能看到脱敏聚合指标，不能浏览员工问题、回答、引用或证据片段；从历史实时记录发起追问时外部查询调用数为 1 且新旧 `run_id` 不同，历史结果不得作为回答证据。

## 同租户跨门店多轮上下文（v1.7，2026-08-27）

左侧当前门店仅表示页面默认浏览范围，不是对话执行边界。用户可在页面停留于 A 店时显式查询同租户授权范围内的 B 店、区域、多家门店或全部门店；结果卡必须分别展示“页面当前门店”和“本轮实际范围”，且查询其他门店不自动修改左侧选择器。

多轮状态区分 `tenant_scope`、`authorized_scope`、`page_scope` 与 `task_scope`。本轮显式门店、已确认结果集合和明确续问优先于页面默认门店；无法唯一判断“这家/这里”指页面门店还是对话门店时必须澄清。租户和实时用户权限是硬边界，单店与多店执行必须共用服务端授权范围解析；无权门店不得触发上游摄像头、抓图、VLM 或 OVD 调用，也不得回退到页面门店。

跨门店续问只继承任务语义，不继承错误证据。例如 A 店检查“红色沙发”后说“再看 B 店”，应继承沙发和红色条件，但重新解析 B 店镜头并抓取 B 店画面；只有明确说“这张图/刚才那张图”才允许复用已归档同帧。说“现在/目前/再看一下”、切换门店/楼层/点位/镜头或指定时间时必须重新取证。任一门店无图、离线、模型失败或低置信均返回 `BLOCKED/UNCERTAIN`，不能归一为“不存在”。

上下文必须持久化为受控 revision，保存实际任务范围、范围来源、动态视觉问题、时间语义和证据 ID，不保存供应商签名 URL、令牌或图片 Base64。刷新和服务重启后可恢复；新会话、其他用户、租户切换、权限撤销或显式“不要沿用”不得继续读取。TTL 到期后不得复用旧证据，但同一用户在同一会话内发出高置信续问时，可在最长 30 天语义保留期内从最近可信视觉 revision/消息懒恢复“上次问了什么、查了哪些门店”，并强制重新校验权限和抓取最新画面。并发请求使用 revision 防止旧请求覆盖新状态。

验收要求：页面 A 查询 B 后，“灰色的呢”继续查询 B；“当前门店呢”切回 A 并重抓；“其他门店也看一下”生成授权范围内的多店任务；跨店模型输入图片全部属于本轮实际门店；旧会话在 context revision 上线前有视觉结果时，“在帮我找一个灰色的沙发”规范为“再帮我…”并恢复视觉任务，不得进入购物建议 OpenQA；单店与多店权限拒绝均发生在上游调用前；结果卡和执行链路显示上下文恢复、决策、范围解析、权限校验、证据模式与最终模型节点。
