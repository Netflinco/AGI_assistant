# 多轮对话上下文承接优化方案 V2：同租户跨门店范围

| 项目 | 内容 |
| --- | --- |
| 版本 | V2.0 |
| 日期 | 2026-08-27 |
| 状态 | P0 核心已实现，节点级回归通过 |
| 替代 | `CONVERSATION_CONTEXT_CONTINUATION_OPTIMIZATION_PLAN_2026-08-27.md` |
| 核心修正 | 门店不是会话上下文的安全边界；同租户、授权范围内允许跨门店承接任务语义，但切换门店或镜头时禁止复用旧画面 |

## 1. 结论

上一版“切换门店即让上下文失效”的设计不成立。产品中的左侧当前门店只是页面默认浏览范围，不等于本轮对话实际执行范围。现有实现已经支持：页面停留在 A 店时，用户显式查询 B 店、区域、多家门店或当前租户全部门店。

V2 采用以下边界：

1. **租户是数据隔离硬边界**：不得自动跨租户读取或继承；切换租户后使用新的认证租户上下文。
2. **权限是执行范围硬上限**：每轮解析出的门店集合都必须与服务端实时计算的授权组织集合校验，权限撤销立即生效。
3. **门店是可变任务槽位，不是会话边界**：当前轮可显式替换、扩大、缩小或比较门店范围。
4. **任务语义可以跨门店继承，媒体证据不能跨门店误复用**：例如从 A 店切到 B 店时可继续检查“灰色沙发”，但必须重新解析 B 店镜头并抓取 B 店画面。
5. **页面范围与执行范围分离显示**：用户不需要先切换左侧门店，结果必须明确说明本轮实际检查了哪些门店。

## 2. 现有实现核对

本次不是凭产品假设修正，而是按现有链路核对：

- `online_agent.py:4145-4172` 会加载当前租户完整组织树和全部门店。
- `online_agent.py:4186-4210` 中，文本显式解析出的 `poi_names` 优先于页面传入的 `context.org_id`；页面门店只在没有显式门店时兜底。
- `server.py:8575-8653` 已识别“所有门店、多家门店、N 家门店、跨门店、区域”等范围。
- `server.py:8734-8757` 明确避免页面当前门店把多门店请求错误压缩成单店。
- `server.py:8760-8836` 已按门店生成在线/离线镜头子任务，并支持排除门店。
- `server.py:5623-5641` 提供组织授权集合与拒绝访问能力；批量链路已做权限过滤。

因此，原问题不是“不支持跨门店”，而是缺少一个统一、可持久化、带来源和权限校验的多轮范围状态。另有一个需要一并修复的安全一致性问题：在线单店路径目前由 `OnlineInspectionAgent` 自行解析全租户组织，但没有像批量路径一样显式接收并裁剪 `allowed_org_ids`；V2 必须把权限校验前移为所有单店/多店路径共用的服务端步骤。

## 3. 四层范围模型

不得继续把 `context.org_id` 同时当页面状态、对话状态和执行状态。新增四层独立范围：

| 范围 | 含义 | 是否可由模型直接决定 |
| --- | --- | --- |
| `tenant_scope` | 当前认证租户，数据隔离边界 | 否 |
| `authorized_scope` | 当前用户在该租户内实时可访问的组织集合 | 否 |
| `page_scope` | 左侧选择器当前门店，仅作为新任务默认值 | 否，来自前端受控上下文 |
| `task_scope` | 本轮/当前任务实际要执行的门店、区域、摄像头集合 | 模型只可识别自然语言表达，ID 必须由后端解析 |

每个 `task_scope` 必须保存来源：

- `EXPLICIT_QUERY`：当前文本显式写了门店/区域/全部门店。
- `DISCOURSE_REFERENCE`：来自“那家店、这两家、失败的门店”等对话指代。
- `INHERITED_TASK`：明确续问，沿用上一任务范围。
- `PAGE_DEFAULT`：本轮没有任何范围表达，使用页面当前门店。
- `CONFIRMED_CLARIFICATION`：用户从候选范围中确认。

## 4. 范围解析优先级

每轮按以下顺序解析，前者覆盖后者：

1. 当前文本显式范围，例如“东莞店”“华南区”“其他门店”“所有门店”“除 A 店外”。
2. 当前文本引用的已知结果集合，例如“异常的三家”“失败的两家”“刚才那两家”。
3. 已确认的消歧答案或待确认 Plan 的范围修订。
4. 高置信续问所继承的活动 `task_scope`。
5. 页面 `page_scope`，仅用于没有续问关系的新任务。
6. 仍无法唯一确定时澄清，不得静默回落到页面门店或全部门店。

解析完成后统一执行：

```text
自然语言范围
  -> 组织/区域/门店候选解析
  -> 同名与层级消歧
  -> tenant_scope 校验
  -> authorized_scope 校验
  -> 在线状态/镜头可用性检查
  -> 固化 task_scope 快照
```

模型只能输出“东莞店、其他门店、失败门店”等受控范围表达和操作类型，不能生成 `tenant_id`、`org_id`、`camera_id`、证据 ID 或绕过权限。

## 5. 多轮范围操作

`ContinuationResolver` 在判断是否续问的同时，必须输出范围操作，而不是只有 `continue=true/false`：

| 操作 | 示例 | 范围行为 | 证据行为 |
| --- | --- | --- | --- |
| `KEEP_SCOPE` | “再找一个灰色的”“背包呢” | 沿用上一任务门店 | 同店同镜头且明确“这张图”才可复用，否则抓最新帧 |
| `REPLACE_SCOPE` | “再看东莞店”“换杭州店” | 用新门店替换旧范围 | 重新选镜头并抓新店画面 |
| `EXPAND_SCOPE` | “其他门店也看一下”“全部门店都查” | 扩大到解析出的授权门店集合 | 按门店生成新子任务，不复用原店画面 |
| `NARROW_SCOPE` | “只看天河店”“只复查失败的两家” | 从当前集合中缩小 | 对剩余门店按时效策略重抓或复用各自证据 |
| `COMPARE_SCOPE` | “把这两家对比一下” | 保留多个有序门店范围 | 使用各门店独立标记的同口径证据；时点不一致必须提示或统一刷新 |
| `RETURN_PAGE_SCOPE` | “当前门店呢”“看看页面这家店” | 显式切回 `page_scope` | 重新抓页面门店画面 |
| `PREVIOUS_SCOPE` | “上一家呢”“回到刚才那家” | 从范围历史恢复前一范围 | 重新校验权限与时效后执行 |

典型行为必须为：

```text
页面当前门店：A
用户：看下 B 店有没有红色沙发
系统：task_scope=B，抓 B 店画面
用户：灰色的呢
系统：task_scope=B，目标改为灰色沙发
用户：其他门店也看一下
系统：task_scope=授权范围内除 B 外的门店，按店执行
用户：当前门店呢
系统：task_scope=A，重新抓 A 店画面
```

## 6. 页面切店与对话范围的关系

页面门店切换不能机械地删除会话事实，也不能机械地把旧任务范围带到新请求。规则如下：

1. 页面切店只更新 `page_scope`，不会修改已经执行、待确认或用于审计的 `task_scope` 快照。
2. 活动范围来自 `EXPLICIT_QUERY` 时，下一句含“再、继续、刚才、那个、其中”等明确续问关系，继续原任务范围；页面必须显示“本轮范围来自对话”。
3. 下一句是完整的新问题且没有续问关系，使用新的 `page_scope` 创建新任务。
4. 活动范围仅来自 `PAGE_DEFAULT` 时，页面切店会结束其“隐式默认”资格；新问题默认使用新页面门店。
5. 页面门店与活动任务门店不同时，“这里/这家”属于歧义表达，应追问；“当前门店/页面这家店”指 `page_scope`，“该店/刚才那家”指最近 `task_scope`。
6. 页面切店不得改变已经生成的 Plan。若用户说“改成 B 店”，创建新 Plan revision 并重新确认；重复确认只执行当前 revision。

## 7. 上下文状态模型

新增专用 `conversation_contexts`，建议字段如下：

| 字段 | 说明 |
| --- | --- |
| `context_id`、`conversation_id`、`tenant_id`、`user_id` | 会话归属与安全边界 |
| `domain`、`task_kind`、`state`、`version` | 视觉巡检、告警查询、周期任务、开放问答等状态 |
| `page_scope_snapshot_json` | 创建时页面范围，仅用于解释来源，不用于绕过当前权限 |
| `task_scope_json` | 实际门店/区域/摄像头范围、范围类型和来源 |
| `scope_history_json` | 最近可引用的范围变化和结果集合 |
| `predicate_json` | 动态对象、属性、关系、数量、否定、异常条件等任务语义 |
| `temporal_json` | 当前、同一帧、历史区间、计划时点等时间语义 |
| `evidence_refs_json` | `evidence_id + org_id + camera_id + captured_at + sha256` |
| `result_refs_json` | 批量父任务、门店子任务、失败/异常门店集合等引用 |
| `created_at`、`updated_at`、`expires_at`、`superseded_at` | 生命周期与并发控制 |

上下文不保存供应商签名 URL、令牌或图片 Base64。上下文读取时重新校验 `tenant_id + user_id + conversation_id + authorized_scope`，不能只相信创建时权限快照。

## 8. 续问决策器输出

建议 Schema：

```json
{
  "decision": "CONTINUE|NEW_TASK|CLARIFY",
  "domain": "VISUAL_INSPECTION",
  "context_id": "ctx_...",
  "scope_operation": "KEEP_SCOPE|REPLACE_SCOPE|EXPAND_SCOPE|NARROW_SCOPE|COMPARE_SCOPE|RETURN_PAGE_SCOPE|PREVIOUS_SCOPE",
  "scope_expression": {
    "include": ["东莞店"],
    "exclude": [],
    "references": []
  },
  "inherit": {
    "predicate": true,
    "scope": false,
    "temporal": false,
    "output_format": true
  },
  "effective_query": "检查东莞店画面中是否存在灰色沙发",
  "evidence_mode": "REUSE_SAME_FRAME|REFRESH_SAME_SCOPE|RECAPTURE_RESOLVED_SCOPE|NONE",
  "confidence": 0.96,
  "reason_code": "EXPLICIT_STORE_SWITCH_WITH_PREDICATE_INHERITANCE"
}
```

两段式实现：

1. 轻量规则只处理明确控制词、显式模式、待确认操作和高确定性范围词。
2. 结构化大模型判断续问关系、被继承的语义维度和范围操作；随后由确定性 `ScopeResolver` 将名称映射为真实组织 ID 并做权限校验。

不得再用固定目标词表判断续问；衣服颜色、背包款式、沙发颜色、商品缺货、地面垃圾、员工在岗、人数、区域关系等都进入统一的 `predicate_json`。

## 9. 证据与时效规则

“继承任务”与“复用证据”必须分离：

1. `REPLACE_SCOPE`、`EXPAND_SCOPE`、跨门店 `COMPARE_SCOPE` 一律按目标门店重新解析镜头和抓图。
2. “这张图里/刚才那张图”可复用归档证据，但证据必须带门店、镜头、拍摄时间和哈希。
3. “现在/再看一下/目前”表示刷新；即使门店未变，也抓最新帧。
4. 指定新楼层、点位、柜台、摄像头或时间范围时重新取证，不得用旧画面替代。
5. 批量比较必须保证各门店使用相同时间口径；无法对齐时展示实际时点并降低结论等级。
6. 某门店无权限、离线、无镜头、抓图失败或模型失败时按门店返回 `DENIED/BLOCKED/UNCERTAIN`，不得拿当前页面门店或其他门店代替，也不得输出“不存在”。
7. 用户权限在两轮之间被撤销时，旧证据不再可读取；上下文保留审计引用但不能继续执行或展示受限内容。

## 10. 路由顺序

```text
认证租户与用户
  -> 显式模式锁和安全操作门禁
  -> 加载待确认 Plan / 活动 conversation_context
  -> ContinuationResolver（关系、继承维度、范围操作）
  -> ScopeResolver（组织解析、消歧、权限、在线性）
  -> DomainRouter / IntentRouter
  -> 单店执行或 Batch 编排
  -> EvidenceResolver / VLM / OVD / 数据查询
  -> 结构化结果与新 context revision
```

补充约束：

- 显式 `OPEN_QA` 不读取企业视觉上下文。
- 显式 `INSPECTION` 不允许 OpenQA 抢路由。
- `AUTO` 模式先做续问关系判断，再决定领域。
- 待确认写 Plan 的“确认/取消/改成……”优先于普通领域路由。
- ScopeResolver 失败时停止，不能让 OpenQA 生成看似合理的替代答案。

## 11. 现有代码改造点

| 层 | 改造 |
| --- | --- |
| `server.py` 对话入口 | 在 `online.handle_message` 前加载活动上下文，统一计算 `authorized_org_ids` 和 `page_scope` |
| 统一 ScopeResolver | 复用现有组织树、批量范围、排除门店和消歧能力，统一返回单店/多店结构 |
| `OnlineInspectionAgent._resolve_fields` | 优先使用服务端已解析的 `resolved_org_ids`；即使 Agent 再解析也必须受 `authorized_org_ids` 限制 |
| OpenQA 前置逻辑 | 移除仅靠 `_references_previous_visual` 的窄词表判定，改用结构化 ContinuationResolver |
| 视觉问题改写 | 用动态 `predicate_json` 组合有效 query，删除按固定对象关键词继承的实现依赖 |
| EvidenceResolver | 依据证据 ID 读取已归档字节；跨门店、跨镜头和“当前”请求按规则重抓 |
| 批量路径 | 将 `task_scope` 固化到父任务和每个门店子任务；结果集合可被后续“失败的两家”等引用 |
| 前端 | 同时显示页面当前门店与本轮实际范围；跨店查询不自动修改左侧门店选择器 |
| 审计 | 记录范围来源、解析前表达、解析后 ID、权限过滤数量、证据模式和 context revision |

| Case | 输入/前置 | 期望 |

### 12.3 权限、失败与任务

| Case | 输入/前置 | 期望 |
| --- | --- | --- |
| P01 | 门店负责人查询无权门店 | 403/权限不足，不泄露门店详情，不回退页面店 |
| P02 | 管理员查 10 店，其中 2 店无权 | 结果显示过滤数量，不暴露无权店名称 |
| P03 | 两轮之间权限被撤销 | 重新校验后阻止继续读取旧证据 |
| P04 | 显式请求其他租户门店 | 不自动跨租户；要求先切换已授权租户 |
| P05 | 3 店中 1 店无在线镜头 | 2 店继续，1 店 `NO_ONLINE_CAMERA`，结果部分完成 |
| P06 | 抓图或模型失败 | `BLOCKED/UNCERTAIN`，不得输出业务阴性结论 |
| P07 | 待确认批量 Plan 后页面切店 | Plan 范围不变；确认执行原 revision |
| P08 | “改成只查 B 店” | 新 revision、重新计算影响范围并重新确认 |
| P09 | “重试失败的门店” | 只创建失败子任务重试，不重复成功门店 |
| P10 | 重复点击确认/网络重试 | 幂等，不重复创建或执行 |

### 12.4 会话与并发

| Case | 输入/前置 | 期望 |
| --- | --- | --- |
| C01 | 新会话/另一个用户 | 不继承原会话上下文 |
| C02 | 同会话刷新或服务重启 | 从持久化 context revision 恢复 |
| C03 | 两个标签页并发修改范围 | 使用版本号拒绝过期写入，避免后到旧请求覆盖新状态 |
| C04 | 请求超时后客户端重试 | 基于 request/plan 幂等键复用结果 |
| C05 | 长会话有多个视觉任务 | 按领域、时效、显式指代选活动任务；低置信时澄清 |
| C06 | 切换租户 | 清空前端旧租户活动态，服务端禁止读取旧租户 context |
| C07 | 视觉巡检后问公开知识问题 | 新建 OpenQA 上下文，不携带企业图片或结论 |
| C08 | OpenQA 后说“继续看刚才门店” | 仅在有明确视觉指代时恢复仍有效的视觉 context |
| C09 | 上一轮无证据/已失败 | 可继承任务语义，但不能伪造 `REUSE` 证据 |
| C10 | 上下文 TTL 到期 | 明确提示需重新取证；任务/审计记录仍保留 |

## 14. 验收门禁

P0 上线前必须满足：

1. S01-S11、V01-V10、P01-P10、C01-C10 全部形成自动化测试，关键跨店用例使用真实组织解析结构，不只 mock 路由结果。
2. 单店视觉、多店即时巡检、周期巡检、告警查询、订阅 Plan、开放问答均回归通过。
3. 任一门店切换场景中，模型输入图片的 `org_id/camera_id` 与结果卡一致；不存在旧店图片进入新店判断。
4. 在线单店和批量路径使用同一个授权范围解析器；无权限门店测试必须证明没有上游抓图与 VLM/OVD 调用。
5. 页面当前门店、本轮实际范围、证据门店、审计门店四者可追溯；有意不一致时展示来源，无意不一致时测试失败。
6. 模型不可用时，高确定性显式范围和规则续问仍可执行；含歧义的“这家/那里”必须澄清，不得猜测。
7. 所有失败、无图、低置信结果保持 `BLOCKED/UNCERTAIN`，不得被文本归一化为“没有”。

## 15. 实施顺序

1. **P0-1 安全与范围底座**：统一 `ScopeResolver`，修复在线单店权限裁剪，落库 `conversation_contexts` 与 revision。
2. **P0-2 多轮语义**：实现 ContinuationResolver、动态 predicate、范围操作和页面/任务范围仲裁。
3. **P0-3 证据链**：实现 EvidenceResolver、跨店重抓、同帧复用、时间模式和失败状态。
4. **P0-4 单店/多店统一**：接通现有批量父子任务、失败集合引用、Plan revision 与幂等。
5. **P0-5 UI 与审计**：展示实际范围和范围来源，补充审计字段。
6. **P0-6 自动化回归**：执行第 12 节全部 case，并对权限、跨店证据和并发用例设置发布阻断。

本版本的最终原则是：**同租户授权范围内可以跨门店承接“要做什么”，但每次范围变化都必须重新确定“去哪里取什么证据”；页面门店只是默认值，任务范围才是执行事实。**
